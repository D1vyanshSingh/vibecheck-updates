01What the tool is, and what it refuses to be

vulnscan is a service scanner that produces a report. It opens TCP connections to a fixed list of ports, works out what is listening, judges that service against a fixed rule set, and renders the result as HTML, JSON, CSV and PDF. It is a single Python package with no third-party dependencies; nmap is optional and shelled out to when present.

Three design commitments explain almost every decision in the codebase. If you understand these, the rest is detail.

CommitmentWhat it means in code
Identify before judgingA port number only selects which rules are worth running. A finding fires only when the protocol family matches what the rule expects, or when the port is honestly marked unidentified. See EXPECTED_FAMILIES and _exposure_confidence (§4).
Evidence over absenceAn unanswered port is recorded as an identification gap, not as a clean result: identification_error, coverage.unidentified, and a "not identified" row in the report (§4, §11).
Reproduce the scanThe report carries the engine, its version, the exact argv, the scan source and platform, the skipped port states, what was not tested, and the raw nmap XML is written next to the report (§2, §11).

What it deliberately does not do

  • No exploitation and no authentication. Nothing sends credentials, nothing writes, nothing escalates. The one place a payload is sent is --lab-exploits, which is hard-wired to 127.0.0.1 and only runs against fingerprints it recognises (§6).
  • No UDP or SCTP. The engine, the probes and the report's coverage text all assume TCP.
  • No version guessing. If the banner does not reveal a version, no CVE is claimed. CVE matching is only ever as good as the identification behind it, and the report says so in its own limits section.
  • No automatic feed downloads during a scan. A scan never touches the network except to reach its targets. The advisory database is built only by --update-db, which is a separate, explicit command (§9).
  • No bundled nmap. It is discovered on PATH or via VULNSCAN_NMAP and invoked as a subprocess. Its licence forbids redistribution, and the point of this project is the report around someone else's detector.

Why this shape? A scanner's reputation is made by what it refuses to claim. Every one of the commitments above exists because the alternative produces confident rubbish: "RDP exposed" on any port 3389, "no findings" on a tarpitted host, or a report nobody can reproduce six weeks later.

The two-network-phase rule. Everything between "services collected" and "findings returned" is pure except two deliberate exceptions: the anonymous-FTP login attempt and the optional TLS-1.0/1.1 handshakes. That is why the checks are cheap to re-run, why the fixtures in tests/test_rule_matrix.py can build a PortService by hand, and why a report can be regenerated from a saved JSON without touching the network.

03The data model

Three objects carry the whole tool. Learn their fields and you can read any function in the package without looking anything up.

Defined in vulnscan/scanner.py as a dataclass. It is created by the scan engine and then mutated by the evidence pass; after that it is read-only. Checks never write to it.

Defined in vulnscan/checks.py. It is deliberately dumb: text, a severity, a confidence, and pointers to the asset. The report dict — the JSON contract

report.build_report returns a plain dictionary with schema version 1.3. Everything else in the report layer renders from this structure, so JSON, HTML, CSV and PDF can never disagree about a fact.

Why derive instead of store? If CVSS were stored on the finding, changing a curated vector would silently leave old numbers in place, and a rule could be edited into a state where its severity and its score disagree. Deriving it at write time means the vector table is the single source of truth — and tests/test_cvss.py pins every vector to the band its rule emits.

04Identity: ports locate, protocols decide

This is the core of the tool. Everything else is bookkeeping around it.

A port number is a hint about where to look, never a fact about what is there. Port 3389 is usually RDP; it is sometimes an HTTPS admin panel, sometimes a honeypot, sometimes an SSH tunnel endpoint. A scanner that reports “RDP exposed” because something answered on 3389 is doing nmap-without--sV, and it is the single largest source of false positives in this class of tool. vulnscan therefore separates locating from deciding.

The four facts that decide a port's fate

1. Familyservice_family(svc) maps the identified service name onto a family through SERVICE_FAMILIES (52 service names → 31 families). If the name is unknown it falls back to transport facts: an HTTP response means http, a completed handshake means tls, otherwise unknown.
2. ExpectedEXPECTED_FAMILIES[port] lists the families that make a rule meaningful on that port. Port 2376 expects {docker, http, tls}; port 3389 expects {rdp} and nothing else.
3. Strengthidentity_source in {nmap, http, banner}, or an nmap claim with conf ≥ 8 and a real protocol name. port is not strong.
4. ConflictTwo strong claims that map to different families, ignoring families that all ride HTTP (a Docker API and an HTTP response are the same protocol seen two ways). Conflicts downgrade to tentative rather than picking a winner.

The decision itself is eight lines:

def _exposure_confidence(svc, expected):
    if identity_conflicts(svc):
        return "tentative"
    if identity_is_strong(svc):
        return "firm" if service_family(svc) in expected else None
    return "tentative"

Read the third line carefully, because it is the whole point: a strong identity that is not in the expected set returns None, and None means the finding is not created at all. A strong identity in the expected set is firm. A weak identity — one nothing proved — is tentative, which still produces a finding, labelled.

SituationResult
3389 answers with an SSH bannerStrong ssh; ssh ≠ rdp → no RDP finding. Nothing claims SSH either: there is no SSH exposure rule at all, only a version fingerprint.
3389 accepts TCP, says nothingWeak identity → tentative RDP finding: “port 3389 is open; the protocol was not confirmed”. Uncertain, not silent.
3389 completes a TLS handshakeStrong tls; family tls ≠ rdp → no RDP finding, and the TLS rules run on their own evidence.
3389 identified as RDP by nmap (conf 10)Strong rdp, family matches → firm. --nse extended adds rdp-ntlm-info output as quoted corroboration — same confidence, better evidence.

What can upgrade a tentative claim

Uncertainty is not permanent — the code looks for proof in this order, each step recorded as its own identity claim:

  1. A curated NSE script answer. SERVICE_PROOF_SCRIPTS maps ports to a script and a marker: 22 → ssh-auth-methods, 445 → smb-os-discovery (OS: line), 3389 → rdp-ntlm-info (Product_Version, Target_Name). A real answer upgrades tentative → firm.
  2. An app-layer probe. A 200 with the product's own markers (Docker's ApiVersion, Elasticsearch's cluster_name, kubelet's pod list) upgrades to certain. A 200 without markers, or a 401/403, proves the product exists but not that it is open → firm.
  3. A protocol handshake the scanner can parse. MongoDB's listDatabases reply with ok: 1 is certain; an auth-required error is firm.

Unidentified is a first-class outcome

UNIDENTIFIED_SERVICE_NAMES is {“”, “unknown”, “tcpwrapped”}. Two paths set identification_error:

  • Native: a connection accepted and then reset/aborted while identifying → “connection reset during identification”. The service name is cleared so no port-table guess can stand in for a protocol.
  • nmap: a service element named tcpwrapped or unknown → “nmap reported tcpwrapped — the port answered TCP but sent no readable protocol”. Its conf value is ignored, because a high confidence in “I could not tell” is not an identification.

That gap then appears in four places: the console note at the end of the scan, coverage.unidentified in the JSON, a row in the report's coverage table, and not identified in the asset inventory CSV. The report also never counts it as a clean port.

The failure this replaced. Before this model, EXPOSURE_RULES was keyed on the port number alone and fired with confidence="firm". Scanning -p all against any host produced a page of confident highs about services that were never there, and a tarpitted port 22 produced nothing at all — the two failure modes that make a scanner untrustworthy at the same time.

05The two engines: nmap and native

Both engines return the same thing — list[PortService] plus a metadata dict — so nothing downstream cares which one ran. The difference is what they can prove and what they cost.

Engine resolution

engines.resolve() is deliberately dull: native never looks for nmap; nmap raises EngineUnavailable rather than silently scanning with something else; auto prefers nmap and records why it fell back. That reason is printed, stored as coverage.fallback_reason, and shown in the report's coverage table — a scan that quietly used the weaker detector would be lying about its own evidence.

The nmap command line

Built by build_argv, passed to subprocess.run as a list. No shell, so nothing in a target or option can be interpreted as a command; the port list is compacted into ranges (-p- when the whole range is requested).

nmap  -sV [--version-intensity N]
      -Pn                   # treat targets as up; ICMP is often filtered
      -n                    # no reverse DNS; names come from the targets
      -T4 --max-retries 2 --host-timeout 300s
      [--script ssl-cert,http-title,… --script-timeout 30s]
      -oX - -p 22,80,443 … host…

The whole subprocess has its own ceiling (process_timeout_s=1800) separate from the per-host timeout, so a wedged nmap cannot hang a scan forever. The XML comes back on stdout and is parsed with ElementTree; the raw text is stashed in meta["_raw_xml"], which the CLI pops and writes next to the report.

What parse_xml keeps, and what it refuses

  • Only state=open ports become services; every other state is counted into skipped_ports (closed, filtered, …) and surfaces in coverage. A filtered port is never mistaken for a clean one.
  • tunnel=ssl + http is renamed https, because nmap reports the pair as ssl/http.
  • The host label is the name the user asked for, then the PTR record, then the address — so a report says scanme.org:22, not 45.33.32.156:22.
  • tcpwrapped and unknown are not identifications. The service name is dropped, identification_error is set, and identity_source becomes "". nmap's conf is ignored in that case: a high confidence in “I could not tell” is still not a protocol.
  • NSE script output is kept only when it is a real answer — empty runs, Script execution failed and ERROR: lines are dropped rather than printed as evidence.

Why nmap's own detection is not simply trusted

The nmap engine still runs _enrich(): for every open TCP port it calls the same collect_evidence the native engine uses. When nmap's name is weak (conf < 8, unknown, or a trailing ?), the evidence pass is allowed to name the port from what the service actually said (guess_names=True). When nmap's name is strong, its product/version is kept and the evidence pass only fills gaps. This is how a host that nmap calls “maybe SSH” gets corrected by an actual banner, and how a verified OpenSSH 9.6p1 keeps nmap's precision instead of being overwritten by a regex that saw less.

The native engine, connection by connection

probe_port is the only place a port is identified, and it is written to spend as few connections as possible. The order is:

  1. TLS-first ports (TLS_PORTS: 443, 465, 636, 993, 995, 2376, 5671, 6443, 8443, 8883, 9443) go straight to a handshake. A refused connection ends the probe as closed, a timeout as filtered — neither gets a second attempt. On success the same socket is reused for the HTTPS request (TLS_HTTP_PORTS).
  2. Everything else gets one plain TCP connect. Server-first services (FTP, SSH, SMTP, MySQL, VNC … — SERVER_FIRST_PORTS) are read immediately; client-first services are sent a read-only probe on that same socket.
  3. First-bytes classification runs on whatever arrived. The classifier checks binary handshakes first (MySQL's protocol byte, PostgreSQL's length-prefixed message, MongoDB's opcode), then textual markers, most specific first: ssh-, rfb 00, redis_version, -err unknown command, stat pid / stat version, 220 (vsftpd/proftpd/pure-ftpd, +ok, * ok, amqp, mysql_native_password, password authentication failed, \xffsmb, http/.
  4. A bare 220 is ambiguous — FTP and SMTP both greet that way — so it is recorded as ftp/smtp and never allowed to overrule a port-based guess. It may still name a port that was otherwise silent.
  5. If nothing plaintext answered, one TLS handshake is tried as a last resort. That is how an HTTPS service squatting on an unusual port is identified instead of being mislabelled from the port table.
  6. Only then may the port table supply a name, and identity_source is set to port — which is exactly the marker the checks treat as not proven.

The connection budget is asserted by tests/test_sniffer.py: one connection for SSH, one for HTTP, one for a waiting service that must be asked, and two for HTTPS on an unusual port (handshake, then a separate request). App-layer probes and the FTP login attempt are the only extra connections, and both are deliberate, read-only requests.

ConstantWhat it holds
PORT_SERVICES58 port → name entries. A guess, used only when nothing on the wire named the service.

Why keep two engines at all? nmap is better at identification and has version probe data this project will never reproduce. The native engine exists so the tool works on a machine with nothing but Python — and so every report can be reproduced by someone who does not have nmap installed. Neither is a shim around the other: they share the evidence pass, the checks and the report.

06Evidence: what is actually said on the wire

All evidence collection lives in scanner.py and is called from exactly one place per engine (collect_evidence for nmap, probe_port for native). The rule for everything in this section: read only. No credentials, no writes, no exploitation.

CollectorWhat it does and why it is bounded
grab_bannerReads at most 4 KB, decodes as latin-1 (so binary handshakes do not raise), returns the first 1 KB plus a note of what was sent. Timeouts and read failures return empty strings with a reason, never an exception.
http_fetchOne GET / (or a product path), explicit Host header including a non-default port, UA vulnscan/0.1, and a 64 KB body cap with a grace period after the headers. Returns status, headers, title and a body preview — nothing is followed, retried or authenticated.
tls_session / probe_tlsHandshake with verification disabled (the certificate is analysed, not trusted), then version, cipher, bits and a decoded certificate: subject, issuer, SANs, notBefore/notAfter, days remaining, self-signed, hostname match. supports_tls_versionPins minimum_version = maximum_version and tries a handshake. Only called with --legacy-tls, because it is two extra connections per TLS service and most engagements do not need it.

The one place a payload is sent on purpose

vulnscan/lab_exploits.py runs fixed, non-destructive proof payloads — an anonymous FTP login, a Redis INFO, a /version on a Docker API, a path-traversal read against vsftpd 2.3.4 — but only for --lab-exploits, only to 127.0.0.1, only when a lab fingerprint matches, and with a response cap. The module has no host argument by design: there is no way to aim it at a real target.

07The rule catalogue

Fifty-seven static rule IDs live in vulnscan/checks.py, and a fifty-eighth family — VS-<CVE> — is generated from the advisory database. They are grouped here by what gates them, because that is the thing you need to know when deciding whether a finding is trustworthy.

run_checks runs three families per service in a fixed order — exposure, HTTP, fingerprints — then the two network-dependent families across the whole service list (anonymous FTP, then TLS with optional legacy handshakes). Findings are then sorted by severity, host, port and rule ID, and given VS-0001… IDs, so numbering is reproducible for the same input.

F. Advisory-derived findings

VS-<CVE> findings come from the SQLite database (§9) and are de-duplicated against the curated rules by CVE, so a matched CVE never appears twice on one service. Severity is NVD's own band; confidence is firm for an upstream version in range and tentative when a distro package revision was detected, because a backport may already have fixed it.

One property worth remembering: every check is a pure function of one PortService (plus, for FTP and legacy TLS, one explicit network call). There is no shared mutable state between checks, no ordering dependency, and no rule that can suppress another rule's finding. That is what makes the rule matrix (§13) possible.

08Severity, confidence and CVSS

Three axes, deliberately independent, because collapsing them is how reports lie. A finding can be high severity and tentative (a possible RDP on a silent port), or low severity and certain (a missing Referrer-Policy).

AxisValuesQuestion it answers
Severitycritical, high, medium, low, informationalHow bad is it if true?
Confidencecertain, firm, tentativeHow sure are we that it is true?
CVSS0.0–10.0 with a vectorWhat does the industry's scoring say, and from which vector?

What each confidence level has actually proved

ConfidenceProvenance in this codebase
certainThe service answered the question itself: redis INFO without auth, memcached stats, an anonymous FTP 230, a Docker /version with markers, a Mongo listDatabases reply, a certificate the scanner parsed, an HTTP response it read.
firmThe protocol identity is proven but the consequence is inferred: a Redis that demands auth, a console returning 401/403, a distro-backported version match, a hostname mismatch, a version-only CVE match on a banner.
tentativeNothing proved the protocol; the port number is the only evidence. Also used when two strong identities disagree, and for distro package revisions.

--strict keeps only certain findings and reports how many it suppressed in the coverage block — the count matters, because a strict report with silent suppression would be worse than a normal one.

Tentative does not mean “ignore”. A tentative finding says “something is listening here and we could not prove what; here is what it would mean if the port means what it usually means”. On a real engagement that is exactly the list you take into the next phase. The only identities that produce no finding are strong ones that contradict the rule — those are the false positives this design exists to remove.

09The offline advisory database

A scan never touches the network except to reach its targets, so CVE matching cannot depend on a live API. vulnscan/advisories.py solves this by turning NVD's CVE JSON into a small SQLite file that is built once and queried locally, read-only, on every scan. Standard library only: sqlite3, urllib, gzip.

Sourcehttps://nvd.nist.gov/feeds/json/cve/2.0/nvdcve-2.0-{year}.json.gz, one gzip file per year
Default yearsthe last six (--db-years 2021,2022 overrides)
Default path$XDG_CACHE_HOME/vulnscan/advisories.sqlite3 (usually ~/.cache/vulnscan/), overridable with $VULNSCAN_DB or --db
Build commandpython3 -m vulnscan --update-db — explicit, and it exits without scanning
Query modefile:…?mode=ro; a scan can never create or modify the database

What one CVE row becomes

NVD describes affected products as CPE criteria nested in configuration nodes, each with an optional version range. rows_from_nvd flattens that into rows keyed by product, not by CPE:

  • _CPE_TO_KEY maps the 13 (vendor, product) pairs worth answering for onto 10 product keys: apache-httpd, nginx, openssh, openssl, mysql, mariadb, postgresql, redis, php, vsftpd. Everything else in NVD is skipped by design — a database that claims coverage it cannot verify is worse than a small one.
  • A range becomes introduced/fixed with inclusive flags taken from NVD's own versionStartIncluding, versionStartExcluding, versionEndIncluding and versionEndExcluding.
  • A single affected release encoded in the CPE string (…:2.4.49:… with no range) becomes exact_version.
  • A bare wildcard with no range and no fixed release is skipped: “all versions, no version information” cannot be graded honestly, so it is not imported.
  • Severity comes from NVD's score (≥9 critical, ≥7 high, ≥4 medium, >0 low), falling back to NVD's label, then to medium. The CVSS vector string is stored verbatim and later becomes the finding's cvss_vector.

The schema

CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT);
CREATE TABLE advisory (
    cve            TEXT NOT NULL,
    product        TEXT NOT NULL,
    introduced     TEXT,      -- versionStartIncluding / Excluding
    start_inclusive INTEGER NOT NULL DEFAULT 1,
    fixed          TEXT,      -- versionEndExcluding / Including
    end_inclusive   INTEGER NOT NULL DEFAULT 0,
    exact_version   TEXT,     -- a single release, no range
    severity        TEXT NOT NULL,
    cvss            REAL,
    vector          TEXT,     -- CVSS:3.1/… verbatim
    summary         TEXT,
    url             TEXT
);
CREATE INDEX advisory_product ON advisory(product);

meta carries schema_version, built_at, advisories, years and source. Those values are what the report prints as “X CVEs, built on …” and what the coverage table quotes when the database is missing.

Matching a detected version

AdvisoryDB.lookup(product, version) fetches the rows for one product and evaluates each range in Python:

exact_version set        →  parse(version) == parse(exact)
introduced set           →  version >  introduced   (or >= if start_inclusive)
fixed set                →  version <  fixed        (or <= if end_inclusive)

Two details matter for correctness:

  • Version comparison is numeric groups, not string comparison. parse_version returns (9, 6, 1) for 9.6p1 and (2, 4, 49) for 2.4.49, and _pad zero-fills the shorter tuple so 1.18 equals 1.18.0. It is deliberately not a full package-version comparison — it matches the ordering NVD's ranges assume for these ten products.
  • One advisory per CVE. NVD often lists several ranges for one CVE; the lookup keeps the row with the highest CVSS and returns sorted results. The report must not repeat the same CVE because two CPE ranges matched.

Distributions and backports: the honest part

split_version separates an upstream version from a package revision: 1.18.0-1ubuntu1 → ("1.18.0", "ubuntu"), -2.el9 → red hat, and when the revision says nothing it sniffs the hints nmap and the Server header provide. The distro name changes the finding, not the match:

  • Upstream version in range → firm.
  • A distro package revision detected → tentative, plus a sentence in the description explaining that distributors routinely backport fixes without changing the upstream version, and a note in the evidence that backport status is unknown.

This is the single most valuable piece of restraint in the tool. A scanner that reports “nginx 1.18.0 is vulnerable” on an Ubuntu host with the security patch applied is not being thorough; it is being wrong in a way that costs the reader hours.

Building and replacing it

build_database writes to a temp file in the destination directory, then os.replaces it into place — an interrupted download can never leave a half-written database where a scan will read it. A missing or corrupt file is not an error at scan time: AdvisoryDB.available is simply false, and the report says CVE matching used the built-in fingerprints only.

Freshness is yours to manage. The database is a snapshot. The report records built_at in metadata.advisory_db and in the coverage table, so a reader can see how old the CVE knowledge was. Rebuild monthly, or before any engagement where version matching will be quoted.

10Guidance: ATT&CK, detection, next step

A severity tells a reader how bad something is. It does not tell the blue team what to watch for or the operator what to try next. vulnscan/guidance.py adds three fields to every finding, keyed by rule_id:

FieldContent
attackMITRE ATT&CK technique IDs with names, chosen from 36 named constants such as T1190 Exploit Public-Facing Application, T1021.001 RDP, T1552.007 Container API, T1610 Deploy Container. Labels for the report, not a claim of observed behaviour.
detectionThe telemetry that would show someone using the exposure — specific log lines, firewall events, TLS handshake patterns.
next_stepA read-only confirmation an operator can run inside the agreed scope, e.g. re-issue INFO to see whether CONFIG SET is accepted.

There are 57 entries. Two fallbacks make sure a finding is never rendered with empty guidance: VS-CVE-* gets a CVE-family default, and anything else gets the generic default. provenance.guidance in the JSON records which one applied — rule, cve-family or default — so it is visible when the tool is speaking generically.

Entry points

is_entry_point(finding) answers the red-team question: could this be used without first winning a credential? Nine rules qualify (anonymous FTP, unauthenticated Redis/memcached/MongoDB, the Docker API over HTTP or TLS-detectable, an open Elasticsearch, an open admin console, kubelet), plus any VS-CVE that is high or critical and not tentative. A distro-backport guess is explicitly not an entry point until someone verifies it.

11The report: JSON, HTML, CSV, PDF

All four artifacts render from the one dict described in §3, so they cannot disagree about a fact. JSON is the contract; HTML is the deliverable; CSV is for the ticketing system; PDF is the same HTML printed.

The HTML report's nine sections

1. Scope and authorisationTargets, port range, method, engagement reference — the part a client checks first.
2. Coverage and provenanceEngine and version, exact command, privileges, NSE profile, skipped port states, unidentified services, app probes run, advisory database and its build date, the “not tested” list.

Printing is treated as a first-class output: A4 page setup, denser type, two finding cards per page, page breaks before per-host blocks, no shadows or interactive chips. The same 90-finding lab scan rendered 193 pages before that tuning and 101 after — the same content, without half-empty pages.

CSV: the asset inventory, fourteen columns

host, ip, port, protocol, service, product, version, cpe,
identified_by, tls, state, findings, critical, high

One row per open service. identified_by is identity_source, which is how a reader can tell a proven service from a port-table guess; the last three columns are counts joined from the findings, so the sheet can be sorted by risk without opening the HTML.

File naming, and why -r matters

report_stem turns the report name into a slug: Unicode NFKD-folded to ASCII, lowercased, every run of non-alphanumerics to a single hyphen, trimmed, capped at 60 characters, with vulnscan- in front and the timestamp behind. -r "ACME Q1 external" yields vulnscan-acme-q1-external_2026-11-06_120000.{json,html,nmap.xml} and a PDF of the same stem. No name at all yields the old vulnscan-report_<stamp>.

PDF without a PDF library

pdf.html_to_pdf finds Microsoft Edge first, then Chrome, then checks PATH for chrome/chromium, and runs --headless --print-to-pdf against a file:// URL. That gives a pixel-faithful render of the styled HTML with no third-party package, and a clear error message when no browser exists. The default destination is the Downloads folder (falling back to Desktop, then home), overridable with --pdf-dir or saved config.

Raw evidence for reproducibility

When the nmap engine ran, its XML is written beside the report as <stem>.nmap.xml and its path recorded in metadata.scan.raw_xml. It is never embedded in the report itself: it is evidence a reviewer can re-parse, not a payload to ship to a client. Together with coverage.command, this is what lets someone else reproduce a finding months later.

How a rule is tested

A case is a PortService built with the minimum evidence a rule needs, then an assertion on what run_checks returns:

# positive: the port answers like Docker, so the finding must appear
DockerOn2375().expect("VS-EXP-DOCKER", severity="critical", confidence="certain")
# negative: same port, an HTTP server with no Docker markers
PlainHttpOn2375().expect_none("VS-EXP-DOCKER")

The negative case is the important half. It is what stops the false positives described in §4 from coming back, and it is the reason a new rule costs two fixtures rather than one.

The live rig

tests/fake_services.py starts deliberately vulnerable services on loopback (anonymous FTP, unauthenticated Redis, an open Docker API, a directory listing, a self-signed HTTPS endpoint, and more), and tests/serve_report.py serves a generated report at 127.0.0.1:8622 for visual review. Both are development tools, not part of the package.

14Recipes: extending the tool safely

Each recipe lists the files to touch and the checklist that means it is actually done. The checklist is not bureaucracy — the coverage tests will fail on a missing piece, which is the point.

1. Add a port-gated exposure rule

  1. checks.py → EXPOSURE_RULES[port]: the 7-tuple (rule_id, title, severity, _cwe(…), description, impact, remediation).
  2. checks.py → EXPECTED_FAMILIES[port]: the family set that makes the rule meaningful. This is what stops it firing on a contradicted port.
  3. checks.py → SERVICE_FAMILIES: add the service name(s) if the protocol is new.
  4. guidance.py → GUIDANCE[rule_id]: _g((T…,), detection, next_step).
  5. cvss.py → CURATED_VECTORS[rule_id]: a vector whose score lands in the declared band.
  6. tests/test_rule_matrix.py: a positive case and a negative case.
  7. scanner.py → PORT_SERVICES: only if the fallback guess should know the port.

Done when: the matrix passes, test_every_rule_vector_lands_in_its_rule_band passes, and test_guidance finds an entry for the new ID.

2. Add an app-layer probe

  1. scanner.py → APP_PROBES[port] = (product, path) and APP_MARKERS[product] = (…) — lowercase substrings unique to that product's response.
  2. checks.py → APP_PROOF_PORTS[port] = product, so the check can upgrade confidence from the result.
  3. If the port must never receive an HTTP request otherwise, check NON_HTTP_PORTS/HTTP_PORTS.
  4. tests/test_probes.py: 200-with-markers, 200-without, 401/403, and wrong product.

Done when: a 200 with markers produces certain, a 401 produces firm, and a different product on the same port produces nothing.

3. Add a curated CVE fingerprint

  1. checks.py → check_fingerprints: match on svc.product and an exact ver tuple; set cve=[…] and a reference URL.
  2. Choose confidence honestly: certain only when the version is unambiguous and no backport is plausible, otherwise firm or tentative.
  3. Matrix cases; the negative case is a nearby version that is not affected.

Done when: the CVE appears once (the advisory path de-dupes by CVE), and a neighbouring version produces no finding.

4. Teach the advisory database a new product

  1. advisories.py → PRODUCT_CPES: add every (vendor, product) CPE pair the product appears under.
  2. advisories.py → product_key: map the detected product name onto the key, with the usual ordering traps (mariadb before mysql, postgres before postgresql).
  3. Make sure scanner._extract_product actually produces that product name from a banner or header.
  4. tests/test_advisories.py: an ingestion case with a fake NVD document and a lookup case for a version in and out of range.

Done when: --update-db then a scan against a matching fixture yields a VS-CVE-… finding with NVD's own vector.

5. Add report content

  1. Put the fact in _coverage (or build_report) first — every artifact renders from that dict.
  2. Render it in render_html; if it belongs in the inventory, add the column to CSV_COLUMNS and the row in write_csv.
  3. Bump REPORT_SCHEMA_VERSION if a new key appears, and note it in the README.
  4. Add a test_report_sections case.

Done when: JSON, HTML, CSV and the PDF all show the new fact, and the schema version reflects the addition.

15Failure modes and known limits

A tool is defined as much by how it fails as by what it finds. This section is the list you should be able to recite in a review, because every entry is a question a competent client will ask.

SymptomCause, and what the tool does about it
Port open, no findings, no serviceThe listener accepted TCP then reset, went silent, or delays every reply (a tarpit). Recorded as identification_error and surfaced in coverage, the console and the CSV — never as a clean port.
Everything filteredA firewall, IPS or rate limiter on the path. Ports are counted in skipped_ports; the report's limits section says absence of a finding is not proof of absence.
Service identified, version wrongThe banner lied or was rewritten by a proxy. Version matching is only as good as identification; no version, no CVE claim.
CVE matched on a patched hostDistro backport. Mitigated by detecting the package revision and downgrading to tentative with an explicit note — not eliminated, because the tool cannot read package changelogs.
CVE missed on a vulnerable hostThe product is outside the ten advisory keys, the version is hidden, or the NVD entry has no usable range. The built-in fingerprints are the only fallback, and the report states which path was used.
Web app seen, findings are genericOne GET / is not a web assessment. Enumeration, authentication and business logic are explicitly out of scope (see _NOT_TESTED).
Host unreachable, scan “clean”Targets are resolved once up front; an unresolvable name falls back to the literal string and produces no open ports. Check hosts_up/hosts_down in metadata.scan before believing a zero.
Different results from another networkVantage point is part of the result. Egress filtering, geo-blocking and CDN edges change what is reachable. coverage.scan_source records where the scan ran.
IPv6-only service invisibleThe native engine resolves AF_INET only. A known limitation, not a policy: it is stated here so it is never a surprise in a report.
UDP services invisibleNo UDP scan by design (DNS, NTP, SNMP, TFTP are common gaps). The limits section says so in every report.
Certificate details missingDER decoding uses CPython's private _test_decode_cert. On failure the TLS checks fall back to handshake facts and the certificate rules simply do not fire.
nmap missing on the engagement boxauto falls back and says why; --engine nmap exits 2 rather than scanning with something else.

Three ways a finding can be wrong

  1. Wrong identification. The port was named from a table rather than the wire. Mitigation: family gating, confidence labels, and the contradicted-port suppression in §4.
  2. Right identification, wrong version. Banner rewriting, backports, or a patch level the banner does not mention. Mitigation: version ranges instead of exact matches, distro awareness, and tentative confidence.
  3. Right facts, wrong judgement. The rule's condition does not actually mean what its severity implies. Mitigation: the rule matrix's negative case, the CVSS band invariant, and prose that states the condition plainly.

Self-test (answers follow)

1. A host has 3389 open and identified as SSH. Why is there no RDP finding?
The identity is strong and its family (ssh) is not in EXPECTED_FAMILIES[3389], so _exposure_confidence returns None and the finding is never created. There is also no SSH exposure rule, so nothing is claimed in its place.
2. Is a tentative finding a warning about scanner uncertainty or about the host?
Both, precisely: it means something is listening on a port whose expected protocol could not be proved. It is still reported because suppression here would hide real exposure.
3. The scan says “no advisory database”. Is that a bug or a configuration state?
A deliberate state. Scans never download anything; --update-db builds the file. The absence is stated in the console, in metadata.advisory_db and in the coverage table so a reader knows CVE matching was fingerprints-only.
4. Which engine's identification wins when both run?
nmap's, unless it is weak (conf < 8, unknown, trailing ?). Then the evidence pass may rename the port from what the service actually sent.
5. Why is regreSSHion's finding tentative when the banner clearly matches?
Because distributions backport the fix without changing the upstream version. The banner proves the version, not the patch level, so the rule says so instead of overclaiming.
6. What tells a reader which detector actually ran?
coverage.engine, engine_version, requested_engine, fallback_reason, argv and command in the JSON, and the coverage table in the HTML.
7. Why is -p all no longer a false-positive factory?
Because a port only selects candidate rules; firing requires a protocol family match or an explicitly unidentified port, and the latter is labelled tentative.
8. Severity says high; the CVSS block says 5.3. What went wrong?
A rule bug: the curated vector does not match the declared band. test_every_rule_vector_lands_in_its_rule_band is designed to catch it in CI rather than in a report.
9. What does one connection per port buy you?
Fewer log lines and alerts on the target, less chance of tripping rate limits, and shorter scans. It is asserted, not assumed: tests/test_sniffer.py counts connections.
10. In the CSV, what is identified_by for, and which value should worry you?
It is identity_source. port means the name came from the port table, so the row is a guess; banner/http/nmap mean something proved it.
11. Can a rule ship without tests?
No. The matrix has a coverage check that fails when an ID has no positive or no negative case.
12. Why store start_inclusive when the column already has introduced?
NVD distinguishes versionStartIncluding from versionStartExcluding. The version string alone cannot express which one applied, so the flag is stored beside it.
13. What happens to an NVD entry with a bare wildcard version and no range?
It is skipped at ingestion: with no range and no fixed release it cannot be graded, and a guess would be indistinguishable from a fact.
14. List the seven things every report says it did not test.
UDP/SCTP and ports outside the list; authentication, credential guessing, exploitation and DoS; application business logic and anything behind a login; services filtered by firewall/IDS/rate limiting; TLS 1.0/1.1 unless --legacy-tls; vulnerabilities needing a version the banner does not reveal; NSE scripts outside the selected profile.
15. Why does --strict print a suppressed count?
Because silent suppression reads as a clean host. The count in coverage.suppressed_by_strict keeps the filter honest.
16. What happens with --engine nmap on a machine without nmap?
Exit 2 with an explicit message. It never quietly falls back — that is what auto is for.

17Glossary

BannerThe opening bytes a service sends, read without being asked (server-first) or after one read-only probe.
BackportA security fix applied to an older upstream version by a distributor. The version number does not change, which is why distro package revisions downgrade CVE findings to tentative.
CPECommon Platform Enumeration, NVD's naming scheme for products (cpe:2.3:a:apache:http_server:2.4.49:…).
CIDRAddress range notation (10.0.0.0/24); targets larger than 1024 hosts are refused rather than truncated.
ConfidenceHow much was proved: certain (the service answered), firm (identity proven, consequence inferred), tentative (nothing proved the protocol).
CoverageThe report block listing what actually ran: engine, argv, privileges, scripts, skipped states, unidentified ports, advisory status, and what was not tested.
CVSS vectorA compact string of metric values (AV:N/AC:L/…) from which the base score is computed. The vector is stored; the score is derived.
Entry pointA finding a red team could use without first winning a credential — anonymous access or an unauthenticated management API.
Filtered / closed / openTimed out or blocked / actively refused / accepted the connection. Only open is investigated; the others are counted.
First-bytes classificationNaming a protocol from what the service actually sent, before any port-table guess is allowed.
NSENmap Scripting Engine. Only scripts nmap tags safe (plus read-only intrusive ones in extended) are ever run.
NVDNational Vulnerability Database; the source of the offline advisory database's CVE JSON 2.0 feeds.
Port-table guessA service name taken from a port number rather than from the wire. Recorded as identity_source: "port" and treated as weak everywhere.
ProvenanceWhere a fact came from — engine, script, advisory build, guidance source, CVSS source — carried in the report so claims can be traced.
Service familyThe normalised protocol group (http, redis, docker, …) that rules compare against. 31 families from 52 service names.
TarpitA listener that accepts connections and then stalls or resets, producing tcpwrapped in nmap and an identification gap here.
tcpwrappednmap's word for “the TCP handshake completed and then it said nothing”. Not a service name, and never treated as one.
Weak identityAn identification that nothing proved: the port table, nmap below conf 8, an unknown or tcpwrapped name.
